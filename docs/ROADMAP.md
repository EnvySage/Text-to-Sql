## 阶段 2 · 单步 SQL 质量

**要回答的问题**：补充哪类知识对准确率贡献最大，各自代价多少？

依据是 baseline 的失败归因：有效执行率 98.8% 而准确率 50.2%，问题在理解不在语法。

每一步单独跑一次评测，形成消融曲线。顺序按预期收益排：

| 步骤 | 内容 | 验证 | 花费 |
|---|---|---|---|
| 2.1 | 列描述注入：读 `database_description/*.csv`，把列含义、取值说明拼进 schema | ✅ 09-25：50.2%，在噪声范围内（基线 47.4–50.2%）；按固定单价成本 ×0.89 | 实际 26.6 credit |
| 2.2 | 样例值注入：每列附带若干真实取值（尤其是枚举类列） | ✅ 09-25：**53.8%**，比基线均值 +5.0，对同期重跑 p=0.009；成本持平 | 实际 13.9 credit |
| 2.3 | 输出列约束：prompt 要求只返回问题问到的列 | 250 题评测 | 💰 ~15 credit |
| 2.4 | 执行反馈重试：报错或空结果时把原文回灌，最多 N 次 | 250 题评测 | 💰 ~20 credit |
| 2.5 | schema 裁剪：只保留相关表（库大时才有意义，先量 token 再决定做不做） | 视情况 | 💰 |

每一步都以**上一步**为基线，不以最初的 baseline 为基线，否则说不清增量来源。

**噪声**：同配置重跑会有约 25 题翻转、±3 个点波动（EVAL 4.1）。每步结论必须用逐题配对 + 显著性检验，不能只看准确率差。

**完成标准**：EVAL.md 里有一条从 50.2% 出发的逐步消融曲线，每一步都有准确率和成本。

**注意**：
- 2.1、2.2 会增加输入 token，要同时看成本
- 2.4 引入工具调用，是第一个真正的 agent 循环，需要先实现 `agent/events.py`
- `agent/baseline.py` 不改，新能力写在新模块里

## 阶段 3 · 多步分析

**要回答的问题**：面对"为什么上个月 GMV 掉了"这类模糊问题，agent 能不能拆解、查证、得出有证据的结论？

| 步骤 | 内容 |
|---|---|
| 3.1 | planner：把问题拆成可查询的子问题，支持根据中间结果改计划 |
| 3.2 | Python 计算沙箱：同比、环比、异常检测等 SQL 不擅长的计算。**先写安全设计再实现** |
| 3.3 | verifier：数值交叉校验（分项加总 = 总数）、量级合理性、口径一致性 |
| 3.4 | 结论生成：每个数字附带来源 SQL |

**评测**：BIRD 是单步题，测不了这一阶段。需要自建 30–50 道多步分析题，标注
"正确结论应包含的关键发现"，指标为关键发现召回率。另建一批故意错误的中间结果，测 verifier 拦截率。

评测集的设计本身需要先和用户确认。
