### 1.1 多方言评测：BIRD Mini-Dev

| 项 | 值 |
|---|---|
| 数据集 | BIRD Mini-Dev，官方同一批题提供 SQLite / MySQL / PostgreSQL 三版标准 SQL |
| 来源 | `https://bird-bench.oss-cn-beijing.aliyuncs.com/minidev.zip`（800 MB） |
| 本地路径 | `eval/datasets/bird_minidev/minidev/`（不进 git） |
| 规模 | 500 题，11 个库；simple 148 / moderate 250 / challenging 102 |
| PG 评测库 | `eval/pg/docker-compose.yml`：官方导出按 `db_id` 拆进 11 个 schema，每道题用 `search_path` 只看得到自己的库 |

- **名字别混**：Mini-Dev 是 BIRD 官方的 500 题子集，按本协议跑出的数字可以引用；
  `eval/datasets/mini/` 是自造的 6 题管线自检集，数字不得引用。
- **不能和 dev 的数字比**：Mini-Dev 里 moderate + challenging 占 70%（dev 随机抽样约 40%），
  它的准确率和 baseline 的 50.2% 不可比。跨方言比较必须在 Mini-Dev 同一批题上各跑一次。
- **只换方言一个变量**：system prompt 只把"SQLite"换成目标方言名，其余一字不改
  （`agent/baseline_dialect.py`）；schema 同样是整库 DDL，不带样例行。
- **成本**：Mini-Dev 比 dev 难，单题成本约为 dev 的 2 倍，250 题约 33 credit、并发 2 约 13 分钟。
- **同一批题**：标准配置同第 2 节（`--limit 250 --seed 0`）。SQLite 版和 PG 版题目文件的题号顺序一致，
  同一 seed 抽到的是同一批题，可以逐题配对比较。

## 2. 标准实验配置

除非实验本身就是在研究某个参数，否则以下参数固定：

| 参数 | 值 | 说明 |
|---|---|---|
| `--limit` | 250 | 从 1534 题中抽样 |
| `--seed` | 0 | 固定种子随机抽样，覆盖全部 11 个库 |
| `--workers` | 2 | 并发 4 会触发网关 503 |
| 模型 | `global:deepseek-v4.1-flash` | 所有角色。09-25 至 10-06 的历史数字用 `cn:` 前缀，是同一个模型换路由名 |
| `sql_gen.max_tokens` | 8192 | 推理模型的思考计入输出预算 |
| `temperature` | 0 | |
| `--max-rows` | 2000 | |

抽样不取前 N 条：BIRD 的题按库聚集，取前 N 条等于只测两三个库。

**30 题的探路跑只用于发现系统性问题**，置信区间约 ±9 个点，数字不得引用。
实测：同样配置，30 题 60.0%，250 题 50.2%。

## 3. 比对口径

实现在 `eval/metrics.py`，每条规则都有对应测试。

| 规则 | 本项目 | BIRD 官方 |
|---|---|---|
| 行顺序 | 默认不敏感；题干要求排序时敏感 | 不敏感 |
| 行重复 | **敏感**（多重集比较） | 不敏感（`set()`） |
| 列顺序 | 敏感 | 敏感 |
| 浮点 | 保留 4 位小数后比较 | 精确比较 |
| `1` vs `1.0` | 相等 | 视实现而定 |
| `True` vs `1` | 相等（SQLite 用 0/1 存布尔） | — |
| 字符串首尾空白 | 忽略 | 不忽略 |
| NULL | 只和 NULL 相等 | 同 |

**和官方口径不同，本项目数字不能直接和 BIRD 排行榜比较。** 对外引用时必须注明
"本项目口径，行重复敏感"。

### 排序判定

`needs_order(question)` 是按词边界的启发式正则，命中 `ordered by` `top N` `highest`
`descending` 等表达时按顺序比对。原则是**宁可漏判，不可误判**——误判会把正确答案判错。

必须用词边界：BIRD 里 `orders` 表随处可见，子串匹配会把
"How many orders are there?" 判成排序题。

### 作废题

标准 SQL 自己执行失败的题从分母中剔除，单独计入 `gold_failed`。
baseline 250 题中有 1 题作废。

## 4. 指标

| 指标 | 定义 | 用途 |
|---|---|---|
| 执行准确率 | 结果集一致题数 / 有效题数 | 主指标 |
| 有效执行率 | 预测 SQL 能执行成功的题数 / 有效题数 | 和准确率的差值指出问题在语法还是理解 |
| 单题成本 | 总 credit / 有效题数 | 含全部重试 |
| 单题 token | 输入、输出分列；缓存命中、思考 token 单列 | 成本归因 |
| 单题耗时 | 从读 schema 到比对完成 | |

任何"准确率提升"的结论都必须同时报告成本变化。

### 4.1 噪声与成本的比较口径（09-25 起，见 D19）

**噪声**：同一配置原样跑两次（`baseline` 与 `baseline-rerun`，同一批 249 题）：
准确率 50.2% vs 47.4%，**25 题翻转**（9 题翻对、16 题翻错），占 10%。temperature 0 也不保证可复现。

- 两次实验逐题配对后，翻转题数在 25 左右都是正常波动；准确率差 3 个点以内不能说明任何事
- 下结论要看配对的精确符号检验：250 题下，真实效果大约要到 5 个点以上才测得出来
- 基线取两次的均值 **48.8%**，不再只认 50.2%

**成本**：网关按 credit 计价，而**单价会变，同一天内也会变**。09-25 这一天：17:30–18:05 的两次运行
单价是平时的 1.5–2 倍，18:07 以后又恢复正常。所以跨时间比实际扣费不行，"同期对照"也不可靠。

- 成本比较一律**按固定单价折算**：用 09-20 baseline 250 题的逐题扣费拟合得到
  未缓存输入 0.0136、缓存输入 0.0009、输出 0.0570（credit / 千 token），拟合值 0.0611 vs 实际 0.0610
- 实际扣费照常记录（记账用），但不用于实验间比较

| 运行 | 实际扣费 / 题 | 按固定单价 / 题 |
|---|---|---|
| baseline（09-20） | 0.061 | 0.061 |
| baseline-rerun | 0.091 | 0.060 |
| coldesc（2.1） | 0.107 | 0.054 |
| colvalues（2.2） | 0.056 | 0.057 |

## 5. 失败归因分类

`runner.print_report` 按以下顺序归类，每道错题只归一类：

| 类别 | 判据 | 通常意味着 |
|---|---|---|
| 没吐出 SQL | 回复中提取不到 SQL | 输出预算不够、格式约束失效 |
| SQL 跑不通 | 预测 SQL 执行报错 | 列名/表名幻觉、方言问题 |
| 模型调用失败 | 重试后仍失败 | 网关问题，**不是模型能力问题** |
| 结果行数不对 | 行数不一致 | 过滤条件、JOIN、GROUP BY 错误 |
| 结果列数不对 | 列数不一致 | 多选或少选了输出列 |
| 结果内容不对 | 其余 | 口径理解、选错表、计算方式 |

"模型调用失败"和"没吐出 SQL"在正常配置下应该接近 0。如果不是，**先修配置再看准确率**——
项目初期这两类曾让准确率从真实的 60% 虚低到 16.7%。

## 6. 结果文件

路径：`eval/results/<label>-<YYYYMMDD-HHMMSS>.jsonl`

- 第 1 行：本次运行的汇总与参数（label、model、n、limit、seed、sample_rows、dialect、questions、accuracy、exec_rate、cost、cost_unit、gold_failed、wall_s、completed、aborted、git_commit、metric_version）
- `git_commit` 带 `+dirty` 表示跑的时候有未提交的代码改动，这种结果不可复现，正式实验前先提交
- **熔断**：连续 3 题模型调用失败（通常是限流）时 runner 停止派发新题，已完成的照常写盘，`aborted` 记录原因。`aborted` 非空的结果文件**数字不得引用**，只作为逐题明细保留
- 第 2 行起：每题一条 `Record`，字段见 `eval/runner.py`

结果文件**进 git**，是所有结论的原始证据。不要删除旧结果，即使它来自有 bug 的版本——
修复前后的对照本身有价值（例如 `probe` 与 `probe2`）。

09-25 之前的结果文件没有 `git_commit` / `metric_version` 字段：它们的代码都在初始提交 `9e22287` 之前，口径为 `2026-09-20`。

## 7. 新增一个实验的流程

1. 在 ROADMAP 里确认这个实验要回答什么问题
2. **先问用户**：250 题一次约 15 credit、15 分钟
3. 用唯一且可读的 `--label` 跑，其余参数保持标准配置
4. 把结果登记进下面的实验登记表，写一句结论
5. 结论和预期不符时，先看失败归因和逐题明细，排除配置问题，再下结论

### baseline 明细

- 按难度：simple 53.8% (78/145) · moderate 45.0% (36/80) · challenging 45.8% (11/24)
- 按库：superhero 75.0% · student_club 71.4% · financial 63.2% · toxicology 60.0% ·
  european_football_2 50.0% · codebase_community 42.3% · thrombosis_prediction 39.4% ·
  card_games 35.5% · formula_1 30.8%
- 失败归因：内容不对 48% · 行数不对 36% · 列数不对 14% · 跑不通 2%
- 调用失败 0，没吐出 SQL 0
- 思考 token 占输出 94.3%，缓存命中 67.1%

**解读**：有效执行率和准确率相差 48 个点，错误集中在理解而非语法。

### coldesc（2.1 列描述注入）明细

和 baseline 同一批 249 题逐题配对（代码版本 `0c28b15`）：

- 准确率 50.2% → 50.2%；都对 112 · **翻对 13 · 翻错 13** · 都错 111；精确符号检验 p = 1.0
- 按难度：simple 53.8% → 55.2% · moderate 45.0% → 43.8% · challenging 45.8% → 41.7%
- 按库变化最大：european_football_2 11→13 · financial 12→9 · toxicology 15→12，其余 ±1
- 单题输入 token 619 → 1863（×3.0），输出 1016 → 850；缓存命中 67% → 83%；总成本 26.6 credit
- 单题实际扣费 0.107。~~相对 baseline ×1.75~~、~~同期 ×1.17~~：两次都被网关单价波动污染（见 4.1 节）。
  按固定单价折算是 0.054，相对 baseline 的 0.061 是 **×0.89**：说明大多命中缓存，而且模型思考变少了
- 没吐出 SQL 3 题（baseline 为 0），都是思考用满 8192 token（同 D9）
- **说明有害的例子**：`financial.account.date` 的说明写"in the form YYMMDD"，实际数据是 `1995-03-24`。
  说明过时，模型照着写出 `date > '961231'`（q183）；q194 同理
- **说明有用的例子**：q1494 从说明里拿到国家代码，把 `'Slovakia'` 改对成 `'SVK'`
- **很多翻转和说明无关**：翻对的 13 题里 5 题是少输出了多余的列，翻错的 13 题里 2 题是多输出了列，
  另有几题是 DISTINCT、并列值取法不同。这是模型两次运行之间的随机差异，说明里没有"该输出哪几列"的信息

**解读**：列说明里既有有用的取值映射，也有和数据对不上的过时格式，两者相互抵消，净效果为 0，成本却涨了 75%。
~~成本却涨了 75%~~（按固定单价其实降了 11%，见上）。
单独做 2.1 看不出收益。两个后续线索：过时格式可以靠 2.2 的样例值纠正（模型能直接看到真实取值）；
列数类翻转是 2.3（输出列约束）的目标。另外，两次运行之间本身有多少随机翻转还没量过，
在量出这个噪声之前，几个点以内的差异都不能下结论。

### colvalues（2.2 列取值）明细

同一批 249 题逐题配对（代码版本 `cd89ce0`）：

| 对照 | 准确率 | 翻对 / 翻错 | p |
|---|---|---|---|
| coldesc（上一步 2.1） | 50.2% → 53.8% | 20 / 11 | 0.15 |
| baseline | 50.2% → 53.8% | 14 / 5 | 0.064 |
| baseline-rerun | 47.4% → 53.8% | 25 / 9 | **0.009** |

- 相对基线均值 48.8%：**+5.0 个点**；有效执行率 99.2%（历次最高）
- **真实取值纠正了过时说明**：2.1 里被"YYMMDD"带偏的 q183、q194 都答对了
  （模型看到样例 `'1995-03-24'` 后写出 `a.date > '1996-12-31'`）；financial 9 → 13 题
- 按库涨得最多：student_club 20 → 23、financial 9 → 13、toxicology 12 → 15（相对 2.1）
- 单题输入 token 3406（baseline 的 5.5 倍），缓存命中 88.6%；输出 866（比 baseline 少 15%，思考变少）
- 按固定单价成本 0.057 / 题，比 baseline 的 0.061 低 6%
- 失败归因：内容不对 53 · 行数不对 44 · 列数不对 16 · 没吐出 SQL 1 · 跑不通 1

**解读**：2.1 + 2.2 合起来有显著收益，而且不增加成本。单看 2.2 相对 2.1 的 +3.6 还不显著（p=0.15），
合理的解释是：列说明提供语义，真实取值纠正说明里的错误格式，两者要一起才起作用。
剩下的错误里"列数不对"占 14%，是 2.3（输出列约束）的目标。

| 对照 | 准确率 | 翻对 / 翻错 | p |
|---|---|---|---|
| outcols（窄）vs colvalues | 53.8% → 55.4% | 14 / 10 | 0.54 |
| **outcols2（宽）vs outcols** | 55.4% → 50.2% | 9 / 22 | **0.029** |
| outcols2（宽）vs colvalues | 53.8% → 50.2% | 9 / 18 | 0.12 |

**列数不对的流动**：16（colvalues）→ 12（outcols）→ 8（outcols2）。约束确实压得住列数错——
outcols2 修好了 outcols 里 7 道（q386、q431、q893、q1002、q1031、q1217、q1393），
但新造了 3 道（q125、q378、q829）。

**宽版为什么更差**：翻错的 22 题里 18 题（82%）是列数以外的错——内容不对 11、行数不对 7、
跑不通 2。内容错从 51 涨到 64。多出来的两条规则（尤其"姓和名要分两列"）把模型带偏，
它开始在别的题上改列结构、聚合方式。失败归因对比：

| 类型 | colvalues | outcols（窄） | outcols2（宽） |
|---|---|---|---|
| 内容不对 | 53 | 51 | 64 |
| 行数不对 | 44 | 43 | 47 |
| 列数不对 | 16 | 12 | 8 |
| 跑不通 | 1 | 3 | 4 |
| 没吐出 SQL | 1 | 2 | 1 |

- 窄版单题成本 0.0603（对 colvalues 0.0573 是 ×1.05），宽版 0.0584；token 都基本持平。
  **成本不是问题，是准确率。**
- **结论**：单次生成 + prompt 这条路对列数错到头了——窄版没用、宽版有害。列数错只能靠
  能自我推理或能对照的机制（3.3 verifier）。代码已删（见 D21），结果文件保留。

### tools 明细（2.4 工具循环）

对照 colvalues（同一批题）：准确率 53.8% → 54.2%，翻对 16 / 翻错 15，**p = 1.0000**。

- 循环确实在工作：245/250 题至少调过一次工具，平均 2.62 步 / 2.77 次调用，只有 1 题撞上限
- 成本几乎持平：输入 token ×3.2（工具结果进 history），但缓存命中 90.7%、**输出 token 反降 31%**
  （思考 808→344——模型拿"调工具"换掉了"思考"）
- **靶子没打中**：设计要修的"SQL 跑不通 + 没吐出 SQL"两轮都各 1 题，一点没动

**解读**：模型愿意自检、也确实自检了，但自检没用——它跑一遍自己的 SQL 看不出"我 WHERE 理解偏了"。
82% 的错题是内容/行数错，工具看不见这类错。

### v4pro 明细（换强模型探天花板）

同 colvalues 配置，只把 `sql_gen` 换成 `cn:deepseek-v4-pro`：准确率 53.8% → 51.0%，
翻对 7 / 翻错 14，p = 0.19（噪声内，方向是**更差**）。

- 思考 token 808 → 1311（+62%），输出 865 → 1370（+58%）
- 实际扣费 14.0 → **147.6 credit（×10.5）**

**解读**：模型想得更多、写得更多，准确率没有提升。**瓶颈不是模型能力。**

### fs / fs-pg 明细（few-shot 检索）

BM25 从"数据集中未被评测的题"取 3 条**同库**示例插进 prompt。两轮都**没有** `--tools`。

| 数据集 | 对照 | 准确率 | 翻对/翻错 | p |
|---|---|---|---|---|
| BIRD dev | colvalues（同为 `cn:` 路由） | 53.8% → **59.4%** | 22 / 8 | **0.016** |
| Mini-Dev PG | minidev-pg-baseline | 47.6% → **55.6%** | 28 / 8 | **0.0012** |

两个数据集独立显著，机制一致：**列数不对砍半**（dev 16→9，PG 23→11）。

**和 2.3 对照**：同一类错误（"不知道该输出哪几列"），prompt 规则治不了（p=0.54，加宽还变差），
**示例能治**。给模型看"这类题长什么样"，比告诉它"要输出该输出的列"管用。

**三条保留**：

1. fs-pg 的基线是 `cn:`、few-shot 是 `global:`，多一个路由变量；dev 那次两轮都是 `cn:`，是干净单变量。
2. 检索出的示例与评测题**模板很接近**（BIRD 题目本身模板化）：0 条完全相同、0 条 Jaccard ≥ 0.9，
   最像的 8/250 在 0.7–0.88，是"同模板不同取值"（`carcinogenic` vs `NOT carcinogenic`）。
   **不是答案泄漏，但给了很强的结构提示——这个数字是上界。**
3. **示例会带偏**：q26（PG）该用 `T1."School Name"`，模型照抄了示例里的 `T2.School`。
   净收益为正，但单题上模型会复制示例的列选择。

### PG 消融曲线（10-07）

路由统一到 `global:` 后重跑，250 题，逐题配对。**形状和 BIRD dev 完全一致**：

| 步骤 | BIRD dev | Mini-Dev PG |
|---|---|---|
| 2.1 列描述 | 中性（p=1.0） | **中性（p=1.00）** |
| **2.2 列取值** | **+5.0（p=0.009）** | **+4.4（p=0.099）** |
| few-shot | +5.6（p=0.016） | +1.6（p=0.62） |
| **few-shot + 业务口径** | — | **+4.4（p=0.0266）** |

两个数据集上 2.1 都中性、2.2 都有效、量级一致（+5.0 / +4.4）——**机制是稳的，不是某个数据集的偶然**。
在 PG 上 few-shot 单独的增益（+1.6）远小于 dev（+5.6），因为 2.2 已经吃掉大部分收益；
但**给示例补上业务口径后，few-shot 重新有效（+4.4）**。

### pg-joinhints 明细（schema 附可连接列）

在 schema 末尾附「同名出现在多张表、且名字像标识符」的列（`*id` / `*code` / `uuid` / `*key`）。

- 对照 pg-colvalues：54.0% → 53.6%，**−0.4，p=1.00**
- **为什么没用**：看错题发现模型**本来 join 就连得对**（q54 / q26 / q25 都正确 join 了 `CDSCode`），
  错在 WHERE 里**选错列**（q28 问 locally funded 用了 `Charter Funding Type`，标准是 `FundingType`）。
  喂连接提示解决的不是真问题。
- 实现时踩到一个坑：只按「同名」会捞出一堆假连接键（`amount` 在三张表里都有、`type` 也是），
  **喂错的比不喂更糟**。加标识符过滤后 11 个库从 70 条降到 33 条。

### fs-pg-ev 明细（few-shot 示例带业务口径）

在 few-shot 示例里附上它自己的 `evidence`（业务口径说明），让模型看到「业务词 → 列」的映射。

- 对照 fs-pg：55.6% → **60.0%**，翻对 16 / 翻错 5，**+4.4，p=0.0266**
- **直接对上错题成因**：错题最大一类是「业务词选错列」，示例带口径就是教这个
- 成本几乎不变：固定单价 0.0740 → 0.0709
- **接用户自己的库时，这个机制的燃料已经现成**：库里的 `user_terms` 表（term / aliases / description）

### minidev-pg-baseline 明细

- 按难度：simple 61.8% (42/68) · moderate 48.0% (59/123) · challenging 30.5% (18/59)
- 按库：superhero 72.0% · financial 64.3% · codebase_community 62.1% · student_club 61.5% ·
  formula_1 44.8% · european_football_2 43.5% · thrombosis_prediction 39.1% · toxicology 34.8% ·
  debit_card_specializing 33.3% · card_games 32.1% · california_schools 27.8%
- 失败归因：行数不对 39% · 内容不对 37% · 列数不对 18% · 跑不通 5% · 没吐出 SQL 1%
- **方言残留**：跑不通的 7 题里 4 题是 SQLite 写法——3 题用 `strftime`，1 题对 `date` 列用 `LIKE`。
  prompt 明确写了 PostgreSQL 仍会发生
- 没吐出 SQL 1 题：思考用满 8192 token（同 D9）
- 调用失败 0，熔断未触发；作废题 0
- 标准答案超过 2000 行的 7 题：4 对 3 错；其中 2 题预测行数远少于 2000，确实错；1 题（346）两边都被截断，
  无法确认，对准确率的影响不超过 0.4 个点
- 思考 token 占输出 93.5%，缓存命中 61.9%；单题成本约为 dev baseline 的 2 倍（题更难，思考更多）
- 总成本 32.8 credit，墙钟 749s（并发 2）

**解读**：有效执行率和准确率相差 49 个点，和 SQLite 上一样，错误集中在理解而非语法。
方言直接造成的失败只有约 4 题（1.6 个点）。PG 相对 SQLite 到底差多少，要在 Mini-Dev SQLite 版
同一批 250 题上跑对照才能回答（预计约 30 credit）。
