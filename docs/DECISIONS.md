# 决策记录

> 每条记录：背景、决定、代价。推翻一条旧决定时不要删除它，新增一条并标注"取代 #N"。

---

### D1 · 选 BIRD 而不是 Spider（09-20）

**背景**：需要一个有客观分数的公开 benchmark。

**决定**：用 BIRD dev。它的数据库更大、有脏数据和缩写列名，还带 `evidence` 业务口径字段，
更贴近真实业务。Spider 太干净，baseline 高，消融曲线没有提升空间。

**代价**：BIRD 数据库较大（最大的 570 MB）；本项目比对口径和官方不同（见 D8），不能直接对标排行榜。

---

### D2 · 不用 LangChain 等 agent 框架（09-20）

**背景**：框架能省样板代码。

**决定**：核心循环自己写。项目的产出是"何时重试、裁掉什么 context"的量化结论，
框架把这些藏在内部就没法测、也没法在面试中讲清楚。

**代价**：适配层、重试、计价要自己写和维护。

---

### D3 · 自己写 provider 适配层，不用 LiteLLM（09-20）

**决定**：`llm/` 下手写 Anthropic 和 OpenAI 兼容两套适配器，约 400 行。

**理由**：两家在工具调用、结果回灌、缓存口径上的差异是真实的工程细节，
自己处理过才能讲清楚。其中缓存 token 口径（Anthropic 不计入 `input_tokens`）不统一的话，
跨模型成本对比全错。

---

### D4 · agent 按角色要模型，不写死模型名（09-20）

**决定**：`Router.for_role("sql_gen")`，角色到模型的映射在 `config/routing.yaml`。

**理由**：成本/准确率实验只需换配置文件。缺 key 时降级到默认角色并警告，
保证单 key 也能开发。

**代价**：降级后的结果和全 key 运行不可比；警告可能被忽略。

---

### D5 · 所有角色只用 `cn:deepseek-v4.1-flash`（09-20，用户决定）

**背景**：本地网关提供 18 个模型。

**决定**：用户明确要求只用这一个模型，不擅自换。

**理由**：一次只动一个变量；这个模型 x0.03 credit，成本低。

**后续**：模型路由实验（阶段 5）需要先征得用户同意。

---

### D6 · 优先用接口上报的实际扣费（09-20）

**背景**：网关在 `usage.credit` 里返回实际扣费。

**决定**：有上报就用上报值（单位 credit），没有才查本地价格表（单位 usd）。
两种单位相加直接抛异常。

**理由**：本地价格表会过期，且是凭记忆写的，未经核实。

---

### D7 · SQL 安全用 AST 白名单 + 只读连接双防线（09-20）

**决定**：sqlglot 解析后只放行 SELECT 类节点；执行时用 SQLite `mode=ro`。

**理由**：正则挡不住注释混淆、多语句拼接。模型不是攻击者，但会在幻觉下写出
`DELETE`；两道防线互相兜底。

---

### D8 · 比对口径：行重复敏感，比官方严（09-20）

**决定**：用多重集而不是集合比较结果。

**理由**：官方 `set()` 会把 `[(1,),(1,)]` 和 `[(1,)]` 判成相等，放过 GROUP BY 写错。

**代价**：数字不能直接和 BIRD 排行榜比较。见 ROADMAP 待决事项 #5。

---

### D9 · baseline 不关思考，把输出预算提到 8192（09-20）

**背景**：`max_tokens=2048` 时，推理模型把预算全部花在思考上，出现空回复。
网关支持关闭思考。

**决定**：baseline 保持默认思考，只把 `max_tokens` 提到 8192。

**理由**：关思考是成本优化，属于阶段 5 的实验，混进 baseline 会让对照组不干净。

**代价**：baseline 单题成本偏高，思考 token 占输出 94.3%。

---

### D10 · 并发默认 2，调用带抖动的指数退避（09-20）

**背景**：并发 4 时网关返回 `503 no_healthy_account`，30 题里 16 题失败。

**决定**：默认并发 2；最多重试 5 次，退避 `min(2^n, 16)` 秒乘以 0.5–1.5 的随机系数。

**理由**：加抖动避免多个 worker 被拒后同时重试。

**代价**：250 题约 14 分钟。

---

### D11 · 先用微型数据集验证管线，再上 BIRD（09-20）

**决定**：`eval/datasets/mini/` 6 题 + 单元测试先把比对和沙箱验证正确。

**理由**：比对逻辑错了会静默产出假数字。实际因此提前抓到 3 个 bug
（截断检测、`orders` 子串误判、布尔语义）。

---

### D12 · 项目放在 D 盘（09-20）

**决定**：项目在 `D:\xs\agent`，uv 缓存在 `D:\xs\uv-cache`（用户环境变量 `UV_CACHE_DIR`）。

**理由**：C 盘剩余空间不足。uv 托管的 Python 解释器仍在 C 盘，迁移风险大于收益。

---

### D13 · Web 界面用 Streamlit，展示执行过程而非聊天框（09-20，规划）

**理由**：目标岗位是 AI 应用 / Agent 开发，不是前端；聊天框看不出 agent 做了什么，
执行过程（计划、SQL、重试、校验、成本）才体现项目价值。投入控制在两天内。

### D14 · 多数据库：一个接口多个实现，SQLite 评测链路不动（09-25）

**背景**：希望 agent 能连 PostgreSQL / MySQL，不止 SQLite。实测现有 guard 在 postgres/mysql 方言下
放行了 `SELECT * INTO t2 FROM t`（PG 里等于建表）、`nextval`/`setval`（改序列）、`pg_read_file`、
`pg_sleep`、`set_config`（能把会话只读关掉）、`FOR UPDATE`（行锁）、`LOAD_FILE`、`SLEEP` 等。
这些在 SQLite 上本来就执行不了，所以之前没暴露。

**决定**：

1. `sandbox/base.py` 定义 `Sandbox` 协议，每种库一个实现，上层只依赖协议。
2. guard 新增拒绝 `Into`、`Lock` 节点；危险函数黑名单按方言分组，但全部生效。
3. 服务端库的第二道防线 = 只读账号 + 只读事务 + 服务端超时，见 DESIGN 3.2。
4. BIRD/SQLite 评测链路、`agent/baseline.py`（prompt 里写死了 SQLite）都不动。

**理由**：黑名单全部生效，是因为 dialect 参数一旦传错就会留出漏洞——`SQLiteSandbox.run()` 原来调
`check()` 时就没传 dialect，恰好靠默认值才对。baseline 保持 SQLite 专用，因为它是 BIRD 上的对照组，
改 prompt 会让既有数字作废。

**验证**：新旧 guard 对 BIRD dev 全部 1534 条标准 SQL、mini 6 条、`eval/results/` 里 296 条历史预测 SQL
的 `check()` 判定和 `ensure_limit()` 输出逐条一致——baseline 50.2% 不受影响，不需要重跑。

**代价**：函数黑名单不可能列全（自定义函数可以有写副作用），服务端库的安全最终靠账号权限，
这是部署前提，代码保证不了。PG/MySQL 的实现要引入 psycopg / pymysql，需要用户同意。

### D15 · PostgreSQL 执行器：账号不合格就拒绝执行（09-25）

**背景**：M.2 实现 `PostgresSandbox`，用户同意引入 psycopg。

**决定**：

1. 每次连接先自检账号：超级用户、任一用户表可写、属于 `pg_read_server_files` 等内置角色，
   **直接拒绝执行**，而不是警告后继续。读 schema 走同一条连接，同样拒绝。
2. 只读事务（会话默认只读 + psycopg 显式 `BEGIN READ ONLY`）+ 服务端 `statement_timeout`。
3. 用服务端游标（`DECLARE CURSOR`）执行：只取 n 行；而且它只接受 SELECT/VALUES。
4. 给模型的报错只保留主信息和 HINT，去掉带 `DECLARE` 包装的 LINE 片段。
5. schema 读 `pg_catalog`，标识符由服务端 `quote_ident` 按需加引号。
6. 公共流程提到 `BaseSandbox`，SQLite 改为继承它。

**理由**：实测只读事务能被 `SET TRANSACTION READ WRITE` 改回去，只有账号权限改不回去，
所以账号层必须强制，警告会被忽略（D4 的教训）。服务端游标同时解决两件事：普通游标会在 execute 时
把整个结果集拉进内存；写语句包进 `DECLARE` 会直接语法报错。

**验证**：PG 集成测试 19 条，每一层防线用"绕过其他层"的方式单独测。SQLite 重构后，
baseline 全部 500 条 SQL（250 标准 + 250 预测）新旧执行器的结果、报错、改写后 SQL 逐条一致；
11 个 BIRD 库的 schema 文本逐字一致。

**代价**：新增依赖 psycopg；每次执行多一次自检查询（本机约 1ms）；
用超级用户做演示会被拒——这是有意的，要先建只读账号（示例见 `tests/pg/init.sql`）。

### D16 · 多方言评测：Mini-Dev，按库拆 schema，prompt 只换方言名（09-25）

**背景**：用户要求先在 PostgreSQL 上跑评测（MySQL 以后再说），模型沿用 `cn:deepseek-v4.1-flash`，并发调低。

**决定**：

1. 数据用 BIRD Mini-Dev 的 PG 版：官方人工改写过标准 SQL，比自己用 sqlglot 转写可信。
2. 官方导出把 11 个库放在同一个 `public` 里，初始化时按 `db_id` 拆成 11 个 schema，
   连接地址带 `search_path`，每道题只看得到自己的库。
3. 新建 `agent/baseline_dialect.py`，只把 system prompt 里的"SQLite"换成"PostgreSQL"；
   `baseline.py` 不动，SQLite 路径直接调用它。
4. PG 评测库数据放 tmpfs，每次启动重新导入。
5. 并发 2（用户同意；并发只影响速度，不影响结果）。runner 加熔断：连续 3 题模型调用失败就停止派发，
   已完成的照常写盘——用户要求"遇到限流就停"，而原来的 runner 只在全部跑完时写盘，中途硬停会丢掉已花钱的结果。
6. 评测库关掉并行查询和同步扫描，沙箱的游标设 `cursor_tuple_fraction=1`：实测这三处会让同一条标准 SQL
   每次结果不同，或和直接执行结果不同。修正后 500 条标准 SQL 在沙箱里重复执行三次结果完全一致。

**理由**：不拆 schema 的话每道题的 prompt 里是 75 张表，长度和难度都变了，
和 SQLite 的数字比不出"方言"这一个变量的影响。prompt 同理，只允许方言名不同。
tmpfs 是为了不往 C 盘的 Docker 磁盘镜像写几 GB 数据（C 盘空间紧张，见 D12）。

**代价**：Mini-Dev 难度分布和 dev 不同，数字不能和 50.2% 比，要在 Mini-Dev 上另跑 SQLite 对照才有结论。
每次启动评测库要重新导入约 1GB 数据。把 Docker Desktop 的磁盘镜像挪到 D 盘后可以改用持久卷。
