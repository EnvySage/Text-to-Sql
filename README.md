# 自主数据分析 Agent

把自然语言问题翻译成 SQL、执行、再给出一句人话结论。支持 **SQLite / PostgreSQL / MySQL**，
自带只读安全沙箱，有命令行和网页两种界面。

项目的重点不是"能跑通"，而是**每一步改动都有可复现的量化证据**——
包括**四个负结果**。做完的实验里有一半是没用的，那些也写在下面。

---

## 结果

BIRD dev，250 题（seed=0，11 个库全覆盖），**逐题配对 + 精确符号检验**。

| 配置 | 准确率 | 成本/题 | 结论 |
|---|---|---|---|
| baseline（整库 schema，单次生成） | 48.8% | 0.061 | 两次重跑差 2.8 个点，**3 个点以内都是噪声** |
| + 列描述 | 50.2% | 0.054 | 噪声内，**无效** |
| **+ 列取值**（每列附几个真实值） | **53.8%** | 0.057 | **+5.0，p=0.009** ✅ |
| + 输出列约束（prompt 规则） | 55.4% / 50.2% | 0.06 | 窄版噪声内、**加宽反而显著变差**（p=0.029）❌ |
| + 工具循环（模型自己试跑 SQL） | 54.2% | 0.057 | **p=1.00，完全无效** ❌ |
| 换强模型（10.5× 价格） | 51.0% | 0.086 | **−2.8，噪声内；思考 token +62% 也没换来提升** ❌ |
| **+ few-shot 检索** | **59.4%** | 0.065 | **+5.6，p=0.016** ✅ |

Mini-Dev **PostgreSQL** 上重跑一遍，形状一致：2.1 中性、2.2 +4.4、few-shot +4.4
（示例带上业务口径后 60.0%，p=0.027）。

**我们的口径比 BIRD 官方严**（行重复敏感），所以这 59.4% 换算成官方口径约 **65%**。

### 一句话结论

> **瓶颈不是模型能力，是任务知识。**

换 10× 价钱的强模型、让它多思考 62%、让它自己试跑验证——**全都没提升**。
few-shot 只加几条示例就 +5.6，而且两个数据集上独立显著。

同一类错误（"不知道该输出哪几列"）：**prompt 规则治不了**（p=0.54，加宽还变差），
**给几条示例就治好了**。模型缺的不是"被提醒"，是"见过这类题长什么样"。

## 快速开始

```bash
cp .env.example .env          # 填 LOCAL_API_KEY / LOCAL_BASE_URL
uv sync --group dev
uv run --group dev pytest tests/ -q          # 244 个测试，不需要 API key 和网络
```

### 命令行

```bash
# 问一句
uv run python -m agent.cli --db <库路径或连接地址> --question "每个月有多少条记录？"

# 存轨迹 / 重放（重放不连模型、不花钱、结果稳定——演示用）
uv run python -m agent.cli --db ... --question "..." --save-trace t.json
uv run python -m agent.cli --replay t.json
```

### 网页

```bash
uv run streamlit run web/app.py
```

重点是**执行过程**——每步的思考、试跑的 SQL、真实返回的表格、最终答案、账目。
不做成聊天框：聊天框看不出 agent 做了什么。

### 评测

```bash
uv run python -m eval.runner \
    --dataset eval/datasets/bird/dev_20240627 \
    --limit 250 --seed 0 --workers 2 \
    --column-descriptions --column-values --fewshot 3 --label my-exp
```

数据集下载见 [docs/EVAL.md](docs/EVAL.md) 第 1 节。

## 架构

```
                 ┌──────────────┐     ┌──────────────┐
   用户问题 ───► │  CLI (rich)   │     │ Streamlit     │   ← 界面层：只渲染，不含逻辑
                 └──────┬───────┘     └──────┬───────┘
                        │   订阅 AgentEvent 事件流  │
                        ▼                      ▼
                 ┌─────────────────────────────────────┐
                 │      agent/  主循环（工具循环）       │   ← 编排层
                 │  思考 → 试跑 → 看结果 → 改 → 交卷     │
                 │  → 真跑一遍最终 SQL → 让模型给结论    │
                 └───┬──────────┬──────────┬───────────┘
                     │          │          │
          ┌──────────▼──┐ ┌─────▼──────┐ ┌─▼─────────────┐
          │   llm/       │ │ sandbox/   │ │ retrieval/    │   ← 能力层
          │ 厂商抽象+路由 │ │ 安全执行    │ │ few-shot 检索 │
          └──────────────┘ └────────────┘ └───────────────┘

          ┌───────────────────────────────────────────────┐
          │ eval/  评测框架：驱动 agent 跑数据集、比对、归因  │   ← 旁路：衡量上面所有东西
          └───────────────────────────────────────────────┘
```

依赖方向只能自上而下。能力层之间互不依赖；`eval/` 可以依赖任何层，任何层不得依赖 `eval/`。

| 目录 | 职责 |
|---|---|
| `llm/` | 与厂商无关的抽象：中立类型、Anthropic / OpenAI 兼容双适配、按角色路由、计价 |
| `sandbox/` | SQL 安全闸门（sqlglot AST 白名单）+ 三种库的只读执行器 + 禁查列 |
| `agent/` | 事件流、工具循环、schema 抽取与裁剪、prompt 模块、CLI |
| `retrieval/` | 列说明读取、BM25 few-shot 检索 |
| `eval/` | 数据集加载、结果集比对、批量评测、失败归因 |
| `web/` | Streamlit 界面 |

## 设计取舍（挑几条）

完整列表见 [docs/DECISIONS.md](docs/DECISIONS.md)（23 条）。

### 不用 LangChain

框架把重试策略和 context 裁剪藏在内部。这个项目的产出恰恰是"在什么条件下重试、
裁掉什么"的量化结论——藏起来就没得测，也没法在面试里讲清楚。

### 安全：两道独立防线，三种库各一套

| 方言 | 第一道：guard | 第二道：连接 | 超时 |
|---|---|---|---|
| SQLite | AST 白名单 + 危险函数黑名单 | `mode=ro` URI | 另起线程调 `interrupt()` |
| PostgreSQL | 同左 | **账号自检**（超级用户 / 任一表可写 → 拒绝执行）+ 只读事务 + 服务端游标 | `statement_timeout` |
| MySQL | 同左 | **账号自检**（`SHOW GRANTS` 出现写权限/管理权限 → 拒绝执行）+ 只读会话 + 服务端游标 | `MAX_EXECUTION_TIME` |

服务端库上，和 `mode=ro` 同等强度的是**账号权限**：会话级只读能被一条 `SET` 改回去（实测），
账号权限改不回去。所以账号自检**必须**有，而且是不合格就拒绝执行，不是警告后继续。

三种库的防线都在真实数据库上实测过（`root` 账号被拒、`DELETE` 被 guard 拦）。

### 比对口径比官方严

官方用 `set()` 比结果集，会把 `[(1,),(1,)]` 和 `[(1,)]` 判成相等——那是 GROUP BY 写错的
典型症状，不该放过。本项目用多重集。**代价**：数字不能直接和 BIRD 排行榜比。

### 成本按固定单价折算

网关的 credit 单价**同一天内都会变**（实测 17:30–18:05 是平时的 1.5–2 倍）。
所以实验间比成本一律按固定单价折算，实际扣费只用于记账。

## 踩坑记录

每条都是实测出来的。**这些比上面的架构图更能说明工程能力。**

### 配置错误让准确率虚低 43 个点

早期 30 题探路跑出 16.7%，看起来像"模型不行"。失败归因表显示 16 题是网关 503、
3 题是思考烧光输出预算——**全是配置问题**。修完是 60%。

**如果没做失败归因，会误以为是模型能力不行，转而去调 prompt——方向完全错。**

### 同配置重跑，25 题翻转

temperature=0 也不保证可复现。所以结论一律看**逐题配对 + 精确符号检验**，
差 3 个点以内不下结论。这也意味着：**250 题只能测出 5 个点以上的效果。**

### 工具挂上去了 ≠ 模型会用

`ask_user` 工具接好、描述也写了，但**模型一次都不问**——它花 20 次工具调用、
56 万 token、撞到步数上限，一路硬猜。

原因：工具描述里写了，**system prompt 里没写**。补上一段"遇到含义不明确的业务名词
先问用户，别自己猜"之后，第一步就问了。

**要模型在某个时机做某件事，得在 prompt 里明说。**

### 禁查名单按子串匹配，误伤了别的列

给含隐私数据的库加禁查名单（`data` / `content`），结果 `metadata` 被 `data` 拦、
`content_hit_count` 被 `content` 拦。模型被拦后花了好几轮猜"为什么 metadata 也被禁"，
最后撞上限。

改成**词边界匹配**后两者都放行，`data` / `content` 仍然拦住。

### 236 个单测全过，一连真库就炸

MySQL 支持写完，单测全绿。接上真库立刻报
`missing "=" after "mysql://..."`——`schema.py` 从两个模块各 import 了一个
`connect_readonly`，MySQL 那个起了别名，但函数里还是写的原名。

**"单测全绿"和"真实环境能跑"是两件事。**

### 结果集比对的三个 bug，全由测试抓出

- **截断检测永远为假**：注入的 `LIMIT` 恰好等于行数上限，取满时无法区分"刚好这么多"和"被截断"。改成注入 `max_rows + 1`。
- **`orders` 里含子串 `order`**：`needs_order()` 用子串匹配，把 `"How many orders are there?"` 判成排序题。改成词边界正则。
- **布尔的比对语义**：SQLite 没有布尔类型，`True` 和 `1` 本来就该判相等，原先的测试断言反了。

教训：**先用自造的微型数据库把比对逻辑验证正确，再动真实数据集。**

## 大库的 schema 裁剪（2.5）

148 张表、2037 列的库上，整库 DDL 要 6 万字符。

**没按关键词挑相关表**——中文提问对英文列名一个词都对不上（"库存数量" vs
`stock_quantity`）。改成**给表名清单 + `get_schema` 工具**，让模型自己按需取，
跟语言无关。

| | 全给 | 表名清单 + `get_schema` |
|---|---|---|
| schema | 56,504 字符 | **2,929** |
| 单题输入 token | 32,171 | **8,657（省 73%）** |
| 答案 | 4 行 | 4 行（一样） |

小库照旧全给（8 张表的库 schema 才 1.6K，多一次工具调用反而慢）。

## 还没做的

- **阶段 3 多步分析**：planner（把模糊问题拆成可查询的子问题）、verifier（数值交叉校验）、
  Python 计算沙箱。现在只会"把问题翻译成一条 SQL"，**问"为什么上个月掉了 40%"它做不了**。
  BIRD 是单步题，测不了这一阶段，要自建评测集。
- **用历史查询当 few-shot 例题**：现在示例来自公开数据集。真实业务库里跑过的 SQL
  才是最好的例题——不用猜出题人的脾气。
- **成本工程**：思考开关、模型路由、成本-准确率帕累托曲线。
